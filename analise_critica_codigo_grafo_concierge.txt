1.1 ThompsonRetriever (SA-CTS probabilístico)
----------------------------------------------------------------------

ARQUIVO:    core/probabilistic_retriever.py (94 linhas)
TESTES:     tests/_test_probabilistic_retriever.py
CRIADO:     Implementa Amostragem de Thompson (SA-CTS) para balancear
            exploração vs explotação na recuperação de memória.

O QUE É:
    O ThompsonRetriever usa a distribuição Beta (parâmetros utility_alpha
    e utility_beta dos metadados vetoriais) para sortear um multiplicador
    probabilístico:
        thompson_multiplier = numpy.random.beta(alpha, beta)
        score_final = similaridade * thompson_multiplier
    Isso permite que memórias com alta incerteza (poucos acessos) sejam
    eventualmente exploradas, enquanto memórias com alta utilidade
    comprovada sejam priorizadas.

POR QUE É ÓRFÃO:
    NENHUM código de produção referencia o ThompsonRetriever:
    - Não está em __init__.py do core/
    - Não está na Fachada Central (core/middleware.py)
    - Não está no HybridSearchEngine (core/hybrid_search.py)
    - Não há MCP tool exposta
    - Único uso é em testes (_test_probabilistic_retriever.py)

    A classe foi provavelmente criada como "feature futura" e nunca
    foi integrada ao pipeline de busca. O HybridSearchEngine continua
    operando deterministicamente (soma ponderada fixa).

IMPACTO:
    - A funcionalidade de exploração probabilística não existe em produção
    - O sistema não aprende com o uso: utility_alpha/beta são inseridos
      como 1.0/1.0 e nunca atualizados (veja item 1.3)
    - Diferencial competitivo perdido vs Zep e Hindsight

COMO CORRIGIR:
    1. Integrar ThompsonRetriever ao HybridSearchEngine:
       - Adicionar parâmetro enable_probabilistic (default False) no search()
       - Quando True, aplicar thompson_multiplier ao score_final
       - Os metadados do VectorSearchResult já contêm utility_alpha/beta
    2. Expor opção nos MCP tools (concierge_search)
    3. Criar tool MCP para atualizar utility (feedback loop)
    ---
    Arquivos a modificar:
    - core/hybrid_search.py (linha ~200: loop de score final)
    - core/probabilistic_retriever.py (export, talvez integrar)
    - interface/mcp_server.py (adicionar parâmetro na tool search)
    - core/middleware.py (passar parâmetro ao search)


1.2 SemanticExtractor (resolução de contradições)
----------------------------------------------------------------------

ARQUIVO:    core/memory_extractor.py (245 linhas)
TESTES:     tests/_test_extraction_noop.py

O QUE É:
    Implementa o pipeline de decisão NOOP para armazenamento de fatos
    semânticos. Compara um novo fato contra fatos existentes (via LLM)
    e decide:
        - ADD: fato completamente novo
        - UPDATE: fato que atualiza/refina um existente (invalidação
          bi-temporal: insere t_invalid no antigo, cria novo)
        - DELETE: fato que contradiz/revoga um existente
        - NOOP: fato redundante (ignora)

    Usa as tabelas semantic_facts (com t_valid/t_invalid bi-temporal)
    e utility_alpha/utility_beta para utilidade Bayesiana.

POR QUE É ÓRFÃO:
    1. A classe SemanticExtractor NÃO é instanciada em lugar nenhum
       do código de produção:
       - Não está no __init__.py do core/ (só exporta ConciergeConfig,
         ProjectIndex, HybridSearchEngine, GrafoConcierge)
       - Não está na Fachada Central (middleware.py)
       - Não há MCP tool exposta para "store_fact" ou "memory_add"
    2. As funções auxiliares insert_semantic_fact() e
       invalidate_semantic_fact() em storage/semantic_logic.py
       só são chamadas pelo SemanticExtractor — que não é chamado.
    3. A tabela semantic_facts é criada no schema mas jamais recebe
       INSERTs em produção.

IMPACTO:
    - Todo o sistema de memória semântica conversacional (fatos bi-temporais
      com resolução de contradições) não funciona em produção
    - As tabelas semantic_facts e user_core_memory existem mas estão vazias
    - O diferencial competitivo de "memória que aprende e resolve
      contradições" não é entregue ao usuário

COMO CORRIGIR:
    1. Adicionar SematicExtractor à Fachada Central (middleware.py)
       como dependência opcional
    2. Criar uma MCP tool (ex: concierge_store_fact) que recebe
       scope_type, scope_id e fact_statement e delega ao extrator
    3. Integrar o extrator ao ciclo de vida dos ActionHooks
       (action_hooks.py) para que fatos sejam extraídos automaticamente
       durante planning/execution/done
    ---
    Arquivos a modificar:
    - core/__init__.py (exportar SemanticExtractor)
    - core/middleware.py (adicionar extractor como dependência)
    - interface/mcp_server.py (nova tool concierge_store_fact)
    - interface/action_hooks.py (integrar no ciclo de vida)

2.1 get_implementations MCP tool retorna SUMMARY em vez do CÓDIGO
----------------------------------------------------------------------

LOCALIZAÇÃO:
    - interface/mcp_server.py:887-908 (_handle_get_implementations)
    - core/middleware.py:479-489 (get_implementations — referência correta)

O ERRO:
    O handler MCP _handle_get_implementations faz:
        node = self._gc.store.get_node(symbol_id)
        ...
        "implementation": node.get("summary", "")
    Mas o CAMPO CORRETO é "content" (que contém o código-fonte real).
    A Fachada Central (middleware.py) implementa corretamente:
        node = self._store.get_node(symbol_id)
        return {"content": node.get("content")}  # ← código real
    Mas o MCP handler ignora a facade e chama a store diretamente.

POR QUE OCORRE:
    O MCP handler foi escrito chamando self._gc.store.get_node()
    (bypassando a facade) e usou "summary" por engano. Provavelmente
    porque summary é o campo mais visível no banco (é populado pelo
    ZoomSummarizer), enquanto content só foi adicionado depois em uma
    migração de schema (schema.py:232-235).

IMPACTO:
    - Usuários da MCP tool get_implementations recebem um resumo LLM
      de 150 tokens em vez do código-fonte real
    - A descrição da tool é enganosa: "Retorna a implementação (bloco
      de código da AST)" — retorna mentira
    - Todo agente que depende dessa tool para ler código-fonte recebe
      dados incorretos

COMO CORRIGIR:
    Opção A (recomendada): Delegar à Fachada
        Substituir o handler para chamar self._gc.get_implementations(symbol_id)
        em vez de self._gc.store.get_node(symbol_id).
        A facade já retorna o campo content corretamente.
    Opção B (mínima): Corrigir o campo
        Trocar node.get("summary", "") por node.get("content", "")
        no handler.

    Arquivo: interface/mcp_server.py (~linha 898)


2.2 Pesos do Hybrid Search no ConciergeConfig são ornamentais
----------------------------------------------------------------------

LOCALIZAÇÃO:
    - core/config.py:46-48 (define weight_vector, weight_fts5, weight_recency_centrality)
    - storage/logic.py:66-68 (define WEIGHT_VECTOR, WEIGHT_FTS5, WEIGHT_RECENCY_CENTRALITY)
    - core/hybrid_search.py:197-198 (chama store.hybrid_search_score_batch)

O ERRO:
    O HybridSearchEngine.search() (hybrid_search.py) recebe um
    ConciergeConfig com os pesos, mas não os utiliza. Em vez disso,
    chama self._store.hybrid_search_score_batch(), que delega para
    storage.logic.GraphLogic.hybrid_search_score_batch().

    O GraphLogic usa DEFINIÇÕES PRÓPRIAS hardcoded:
        WEIGHT_VECTOR = 0.50
        WEIGHT_FTS5 = 0.25
        WEIGHT_RECENCY_CENTRALITY = 0.25
    que são IDÊNTICAS às do config — mas INDEPENDENTES.

    Se alguém alterar os pesos no ConciergeConfig (ex: 0.40/0.30/0.30),
    o efeito real no score final será ZERO, porque o GraphLogic ignora
    o config e usa suas constantes hardcoded.

POR QUE OCORRE:
    O ConciergeConfig foi adicionado posteriormente como "fonte única
    de verdade", mas o GraphLogic (que é mais antigo) não foi refatorado
    para consumi-lo. Ninguém percebeu o desalinhamento porque os pesos
    default são os mesmos nos dois lugares.

IMPACTO:
    - Qualquer tentativa de calibrar os pesos do Hybrid Search via
      ConciergeConfig será ignorada silenciosamente
    - O sistema é menos configurável do que a arquitetura documenta
    - Manutenção futura pode criar divergências acidentais

COMO CORRIGIR:
    1. Fazer GraphLogic aceitar um ConciergeConfig opcional no __init__
    2. Se config for fornecido, usar config.weight_vector etc.
       em vez das constantes hardcoded
    3. Se não for fornecido (backwards compatibility), usar defaults
    4. Atualizar SqliteStore para passar o config ao GraphLogic
    ---
    Arquivos a modificar:
    - storage/logic.py (linhas 56-68 e __init__)
    - storage/store.py (passar config ao GraphLogic)
    - core/hybrid_search.py (opcional: poderia passar via store)

3.1 verify_sync() carrega TODOS os metadados na RAM
----------------------------------------------------------------------

LOCALIZAÇÃO:    storage/vector_store.py:517-563 (método verify_sync)
SEVERIDADE:     ALTA (crash em escala)

O PROBLEMA:
    O método verify_sync() faz:
        all_data = self._collection.get(include=["metadatas"])
    que carrega TODOS os IDs e metadados da coleção inteira do ChromaDB
    na memória RAM de uma só vez, sem paginação.

    Em projetos pequenos (centenas de vetores) isso é aceitável. Em
    projetos com dezenas de milhares de vetores, causará MemoryError
    (OOM — Out of Memory).

    Compare com o QdrantVectorStore.verify_sync() (vector_backend.py:277-305)
    que usa scroll paginado corretamente:
        offset = None
        while True:
            res, next_offset = self._client.scroll(..., limit=100, offset=offset)
            ...
            if not next_offset: break

POR QUE OCORRE:
    O ChromaDB não tem uma API nativa de scroll/iterator tão clara
    quanto o Qdrant. O desenvolvedor optou pela abordagem "get all"
    por simplicidade, sem considerar escalabilidade.

IMPACTO:
    - O Reconciliation Loop (chamado pelo Janitor e pelo GC pós-mine)
      quebrará silenciosamente ou consumirá memória excessiva em
      projetos médios/grandes
    - O JanitorService pode crashar a aplicação durante manutenção
      noturna se a base tiver muitos vetores

COMO CORRIGIR:
    Opção A (recomendada): Implementar paginação via IDs
        Dividir a consulta em lotes usando limit + offset manual:
        1. Primeiro obter apenas os IDs (sem metadatas) via get(ids=...)
        2. Processar em lotes de BATCH_SIZE=100
        3. Para cada lote, obter metadatas e verificar
    Opção B: Usar a API count() + get paginado do ChromaDB
        ChromaDB não suporta paginação nativa via get(), mas é
        possível usar limit + offset se a coleção usar IDs
        sequenciais.

    Arquivo: storage/vector_store.py:517-563


3.2 Janitor acessa cadeia de atributos privados
----------------------------------------------------------------------

LOCALIZAÇÃO:    services/janitor.py:175-181

O PROBLEMA:
    O método is_system_active() do JanitorService faz:
        if self._store and hasattr(self._store, "_conn_mgr") ...
            conn_mgr = self._store._conn_mgr
            if hasattr(conn_mgr, "_write_queue") ...
                write_q = conn_mgr._write_queue
                if hasattr(write_q, "_queue") ...
                    if not write_q._queue.empty():
                        return True

    Isso acessa uma cadeia de 3 atributos privados (não públicos):
        SqliteStore._conn_mgr._write_queue._queue

    Se QUALQUER um desses atributos for renomeado (refatoração),
    o Janitor quebra silenciosamente.

IMPACTO:
    - Alta fragilidade a refatorações
    - Código difícil de testar (precisa mockar a cadeia inteira)
    - Violação clara do princípio de encapsulamento (Law of Demeter)

COMO CORRIGIR:
    1. Adicionar um método público em SqliteStore:
        def is_write_queue_empty(self) -> bool:
            """Retorna True se a fila de escrita não tem jobs pendentes."""
            return self._conn_mgr.is_write_queue_empty()
    2. Adicionar método público em ConnectionManager:
        def is_write_queue_empty(self) -> bool:
            return self._write_queue.is_empty()
    3. Adicionar método público em SerializedWriteQueue:
        def is_empty(self) -> bool:
            return self._queue.empty()
    4. Substituir a cadeia em Janitor por:
        self._store.is_write_queue_empty()
    ---
    Arquivos a modificar:
    - storage/connection.py (SerializedWriteQueue.is_empty, ConnectionManager.is_write_queue_empty)
    - storage/store.py (SqliteStore.is_write_queue_empty)
    - services/janitor.py (linhas 175-181)


3.3 chunk._node_id setado dinamicamente (encapsulamento violado)
----------------------------------------------------------------------

LOCALIZAÇÃO:    ingestion/orchestrator.py:358

O PROBLEMA:
    O IngestionManager._step_store_sqlite() faz:
        chunk._node_id = chunk_node_ids[i]

    chunk é uma instância de ParsedChunk (dataclass em parser.py),
    e _node_id NÃO é um campo definido na dataclass. O código
    adiciona um atributo externamente, violando o contrato da
    dataclass.

IMPACTO:
    - O tipo do chunk é semanticamente mutilado
    - Editores/IDEs não autocompletam _node_id
    - Se a dataclass for congelada (frozen=True) ou usar __slots__,
      o código quebra
    - O campo é acessado em _step_embed (orchestrator.py:491):
        node_id = getattr(chunk, "_node_id", None)
    O fallback getattr(..., None) indica que o código já sabe que
    o atributo é frágil.

COMO CORRIGIR:
    1. Adicionar node_id como campo opcional na dataclass ParsedChunk:
        node_id: Optional[int] = None
    2. Substituir chunk._node_id = valor por chunk.node_id = valor
    3. Em _step_embed, usar chunk.node_id diretamente, sem getattr
    ---
    Arquivos a modificar:
    - ingestion/parser.py (dataclass ParsedChunk: adicionar node_id)
    - ingestion/orchestrator.py (linhas 358, 491)


3.4 main.py síncrono (sem suporte async)
----------------------------------------------------------------------

LOCALIZAÇÃO:    main.py:219

O PROBLEMA:
    O servidor MCP é iniciado com:
        server.run(transport=TRANSPORT)
    que é uma chamada BLOQUEANTE. O loop principal não pode fazer
    mais nada enquanto o servidor estiver rodando, e não há suporte
    a event loop asyncio.

IMPACTO:
    - Escalabilidade limitada: não é possível atender múltiplas
      conexões simultâneas
    - Sem suporte a transport SSE (Server-Sent Events) que seria
      necessário para deploy web
    - O JanitorService contorna isso rodando em thread separada,
      mas o servidor em si é single-threaded

COMO CORRIGIR:
    Opção A: Usar FastMCP com uvicorn (recomendado)
        O FastMCP suporta run_async() ou ser montado em uma ASGI app.
        Substituir server.run() por:
            import uvicorn
            uvicorn.run(app, host=host, port=port)

    Opção B: Usar threads para cada conexão
        Menos recomendado mas mais simples: usar
        server.run(transport="sse") dentro de um thread pool.

    Observação: O Google Generative AI (gemini) e OpenAI têm clientes
    síncronos, então seria necessário também refatorar LLMAdapter
    para async ou rodar chamadas LLM em thread pool.

    Arquivo: main.py (linha 219)

3.7 SQLiteStore.close() só fecha conexão da THREAD ATUAL
----------------------------------------------------------------------

LOCALIZAÇÃO:    storage/connection.py:230-241

O PROBLEMA:
    ConnectionManager.close() faz:
        conn = getattr(self._local, "conn", None)
        if conn:
            conn.close()
            self._local.conn = None

    Isso fecha apenas a conexão de LEITURA da THREAD ATUAL.
    Outras threads que tenham conexões de leitura abertas via
    threading.local() terão suas conexões vazadas (nunca fechadas).

IMPACTO:
    - Em cenários multi-thread (ex: Janitor), as conexões de leitura
      de threads auxiliares não são fechadas no shutdown
    - Vazamento de recursos (file descriptors) em execução prolongada
      com criação/destruição frequente de threads

COMO CORRIGIR:
    Manter um registro de todas as conexões de leitura criadas:
    1. Usar um dict thread_id → connection em vez de threading.local()
    2. No close(), iterar sobre TODAS as conexões e fechá-las
    Alternativa: fazer as threads fecharem suas próprias conexões
    (mas isso depende de cooperação externa).

    Arquivo: storage/connection.py (linhas 230-241)


3.8 Sem retry na conexão Qdrant (modo NO-OP permanente)
----------------------------------------------------------------------

LOCALIZAÇÃO:    core/vector_backend.py:52-72

O PROBLEMA:
    Se o Qdrant estiver fora do ar no momento da inicialização,
    o QdrantVectorStore entra em modo NO-OP PERMANENTE:
        if not self._available:
            self._client = None
            return

    Não há tentativa de reconexão periódica. Depois que o Qdrant
    volta, o store continua em NO-OP.

IMPACTO:
    - Em deploy com Qdrant, uma queda temporária do banco vetorial
      torna as buscas semânticas permanentemente vazias até o
      próximo restart do Grafo Concierge
    - A mensagem de erro é apenas um log warning — operação
      silenciosamente degradada

COMO CORRIGIR:
    Implementar reconexão com backoff:
    1. Adicionar método _ensure_connected() que tenta reconectar
       antes de cada operação (search, store, delete)
    2. Usar exponential backoff (1s, 2s, 4s, 8s, max 60s)
    3. Se reconnect bem, sair do modo NO-OP
    ---
    Arquivo: core/vector_backend.py (vários métodos)

4.1 detect_communities faz JOIN desnecessário em nodes_fts
----------------------------------------------------------------------

LOCALIZAÇÃO:    services/janitor.py:476-487

O PROBLEMA:
    A query para detectar super-nós (nós com in_degree >= threshold) faz:
        SELECT n.id
        FROM nodes n
        JOIN nodes_fts f ON n.id = f.rowid   ← JOIN DESNECESSÁRIO
        LEFT JOIN edges e ON n.id = e.target_id
        WHERE n.project_uuid = ? AND n.status = 'ACTIVE'
        GROUP BY n.id
        HAVING COUNT(e.source_id) >= ?

    O JOIN com nodes_fts (tabela FTS5) não é usado em nenhum lugar
    da query — nem no WHERE, nem no SELECT, nem no HAVING. Ele é
    completamente desnecessário. Uma simples query em nodes + edges
    teria o mesmo resultado com menos overhead.

IMPACTO:
    - Performance degradada: o SQLite precisa fazer o JOIN com a
      tabela virtual FTS5, que envolve overhead de indexação
    - Pode causar slowdown no Janitor para projetos grandes

COMO CORRIGIR:
    Remover o JOIN com nodes_fts:
        SELECT n.id
        FROM nodes n
        LEFT JOIN edges e ON n.id = e.target_id
        WHERE n.project_uuid = ? AND n.status = 'ACTIVE'
        GROUP BY n.id
        HAVING COUNT(e.source_id) >= ?

    Arquivo: services/janitor.py (linhas 476-487)

4.4 Prompt Armor com tag XML inventada
----------------------------------------------------------------------

LOCALIZAÇÃO:    ingestion/parser.py:36-37

O PROBLEMA:
    O Prompt Armor envolve chunks de código em tags XML inventadas:
        <raw_data_do_not_execute>...</raw_data_do_not_execute>

    Essa é uma tag que o desenvolvedor inventou — não é um padrão
    conhecido (como <system> ou <human> do Anthropic). LLMs podem
    ou não respeitar essa tag consistentemente.

IMPACTO:

      código nessas tags
    - Falsa sensação de segurança

COMO CORRIGIR:
    Opção A: Usar padrão estabelecido ex: XML comments (<!-- -->) ou
        <artifact> tags que alguns provedores reconhecem
    Opção B: Substituir por sanitização real (escapar caracteres
        especiais, remover backticks, etc.)

    Arquivo: ingestion/parser.py (linhas 36-37 e usos)
