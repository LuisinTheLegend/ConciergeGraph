Data: 2026-10-28
Estado do repositorio: HEAD dd92d35 (nenhuma mudanca de producao feita na 4.2e ate agora)

======================================================================
1. RESUMO EM POUCAS LINHAS
======================================================================
- Pelo cliente MCP real (stdio), a primeira chamada que precisa do modelo de
  embedding (concierge_mine OU concierge_search) TRAVA para sempre no Windows.
- A thread principal do servidor fica presa em "import scipy.special" (extensao
  C _ufuncs), chamado por sklearn, chamado por sentence_transformers.
- O mesmo codigo, fora do servidor MCP (chamada direta em processo), funciona:
  gc.mine() terminou em 41,54 s.
- Quando o import de sentence_transformers e feito de forma SINCRONA na thread
  principal ANTES de server.run(), a busca pelo MCP funciona (22,7 s no total).
- Quando o mesmo import e feito numa THREAD daemon iniciada logo antes de
  server.run() (que e exatamente o desenho da 4.2e), o servidor TRAVA.
- Conclusao parcial: o aquecimento em thread pedido na 4.2e, do jeito
  especificado, NAO conserta o problema. Aguardamos decisao do usuario.

2. CONTEXTO: O QUE A 4.2e QUERIA FAZER
======================================================================
- A 4.2d tirou ~11 s do bootstrap tornando o import de sentence_transformers/
  torch preguicoso (lazy). O custo foi movido para a 1a chamada que gera
  embedding: 15,7 s, 23,06 s e 25,07 s em medicoes anteriores.
- A 4.2e propoe carregar o modelo numa thread em segundo plano logo antes de
  server.run(), para esconder esse custo, e medir a 1a chamada de verdade pelo
  cliente MCP real (a ferramenta antiga, scratch/mcp_e2e_profile.py, chamava as
  ferramentas com parametros invalidos e nunca minerou nem buscou; o tempo de
  ~0,002 s era erro de validacao, nao medicao).
- Foi criada a ferramenta valida scratch/evidencia_4_2e/mcp_e2e_v2.py (cliente
  MCP stdio real, parametros reais, valida isError/success, conta vetores no
  Chroma, valida resultado da busca).

======================================================================
5. HIPOTESES DESCARTADAS (e uma retratacao)
======================================================================
- HIPOTESE DESCARTADA: "uma thread bloqueada lendo stdin trava o import do
  scipy no Windows". Foi afirmada como "confirmada 100%" durante a
  investigacao, mas isso foi precipitado. Matriz de 4 casos isolados
  (repro_matrix.py: import sem leitor de stdin; thread bloqueada em
  sys.stdin.buffer + import na main; idem + import em thread secundaria; stdin
  DEVNULL) terminou OK em 1-2 s em todos. A hipotese esta REFUTADA.
- HIPOTESE NAO TESTADA, DESCARTAR: "bloqueio de sockets do sandbox causava o
  travamento". Nunca foi verificada. (Os testes que travavam em sandbox e os
  que passaram com BypassSandbox variaram junto com outras coisas; nao ha prova.)
- HIPOTESE DESCARTADA: "o SUMMARIZE com chamadas LLM falhas (gRPC/asyncio
  aninhado) deixa estado que trava o import". A busca sem SUMMARIZE tambem trava.

======================================================================
6. HIPOTESE ATUAL (NAO CONFIRMADA)
======================================================================
O import de extensoes C do scipy (scipy.special._ufuncs) trava no Windows
quando o loop asyncio do servidor (ProactorEventLoop) ja esta ativo ou esta
sendo criado. Se o import termina ANTES de o loop existir (sincrono antes de
server.run), funciona. Se o import corre em paralelo com o inicio do servidor
(thread), ou depois dele, trava.
Isto e coerente com todos os dados acima, mas o mecanismo exato (DllMain /
loader lock / outra interacao do Proactor) NAO foi isolado. Os dados de
sincrono-vs-thread sao de uma unica execucao cada.

======================================================================

     bootstrap(); teria de ser feito em main(), fora de bootstrap().

   que trava (scipy.special e possivelmente sklearn), antes de server.run(), e
   deixar o resto (torch, carga do modelo) para thread/lazy.
   + Se so o scipy travar, preserva quase todo o ganho da 4.2d.
   - Ainda nao testado; torch/outros tambem podem travar. Teste de ~2 min.
   - Dentro do escopo (apenas main.py).
