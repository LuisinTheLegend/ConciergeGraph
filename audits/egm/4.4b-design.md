# Technical Audit: Concurrency Architecture & Resilience of `SerializedWriteQueue`

**Target Scope:** `interface/queue_writer.py` (and corroborating database subsystems in `core/database.py`, `storage/store.py`, `interface/mcp_server.py`)  
**Standard:** Production-grade concurrency and resilience standards for multi-threaded SQLite embedded databases. Zero deadlock potential, bounded wait times, fail-fast / clear typing upon unrecoverable crashes, clean worker lifecycle.

---

### Finding 1: Unchecked Handshake Timeout & Inverted Wait Budget Leading to Uninitialized Enqueueing
* **Severity:** Blocker
* **Affected Scope:** `interface/queue_writer.py:36-37`, `65`, `226-250` (`READY_TIMEOUT_SECONDS`, `run()`, `execute_write`)
* **Finding & Recommendation:**
  * **Flaw:** There is a severe timeout inversion and a missing validation check in the handshake synchronization. In `run()`, connection attempts use `sqlite3.connect(..., timeout=30.0)`. In SQLite, `conn.execute("PRAGMA journal_mode=WAL;")` honors this 30-second busy timeout. With `MAX_CONNECT_RETRIES = 5`, startup connection attempts under persistent lock contention can block for up to `5 * 30.0s = 150s` plus backoff. However, `READY_TIMEOUT_SECONDS` is hardcoded to only `10.0s`.
  * **Race / Failure Mode:** In `execute_write` (lines 226–227):
    ```python
    if self.is_alive() and not self._ready.is_set():
        self._ready.wait(timeout=READY_TIMEOUT_SECONDS)
    ```
    The boolean return value of `self._ready.wait(...)` is ignored, and there is no subsequent check confirming `if not self._ready.is_set():`. When 10.0 seconds elapse while Attempt 1 is still blocking in SQLite:
    1. `_ready.wait()` times out and returns `False`.
    2. `self._startup_error` is still `None` (Attempt 1 has not raised yet).
    3. `self.is_alive()` is still `True` (worker thread is actively blocked in SQLite).
    4. `execute_write` falls through to line 237 and pushes `(query, params, response_queue)` into `self.queue` on an unready queue with no established database connection!
    5. `execute_write` enters the polling loop with `EXECUTE_TIMEOUT_SECONDS = 30.0` and times out at $T=40\text{s}$, returning `(False, TimeoutError)`.
    6. The caller receives a `TimeoutError` instead of `sqlite3.OperationalError: database is locked`, completely masking the root cause.
    7. The orphaned write remains trapped in `self.queue` for over 110 additional seconds until Attempt 5 finally raises and drains the queue into dead caller response queues.
  * **Recommendation:**
    1. Guard the handshake explicitly:
       ```python
       if not self._ready.is_set():
           if not self._ready.wait(timeout=READY_TIMEOUT_SECONDS):
               return False, TimeoutError(f"SerializedWriteQueue worker failed to initialize within {READY_TIMEOUT_SECONDS}s.")
       ```
    2. Align timeout budgets: ensure `READY_TIMEOUT_SECONDS >= (connect_timeout + total_backoff)` or configure `sqlite3.connect(timeout=...)` during startup to a low bounded threshold (e.g. 2.0s) so retries execute rapidly within the budget.

### Finding 2: Unbounded Queue with No Backpressure Inducing Livelock and Deadline Starvation
* **Severity:** Blocker
* **Affected Scope:** `interface/queue_writer.py:54`, `214-250` (`self.queue`, `execute_write`)
* **Finding & Recommendation:**
  * **Flaw:** `self.queue` is instantiated as `queue.Queue()` with default `maxsize=0` (unbounded). Under concurrent multi-agent ingestion or high write contention, writes arrive faster than SQLite's serialized single-threaded disk writes (`synchronous=NORMAL`).
  * **Failure Mode:**
    1. **Memory & Synchronization Bloat:** Every call to `execute_write` allocates an ephemeral `queue.Queue()` instance with its own internal `threading.Lock` and `threading.Condition` primitives. Queuing 50,000 requests allocates 50,000 synchronization objects in heap memory.
    2. **Cascading Timeout Collapse (Livelock):** If queue depth exceeds 30 seconds of processing latency, waiting caller threads hit `EXECUTE_TIMEOUT_SECONDS = 30.0` and return `(False, TimeoutError)`. However, their tasks remain queued in `self.queue`. The worker thread does not track caller deadlines or cancellation; it continues executing stale, abandoned writes indefinitely. Fresh writes are queued behind thousands of zombie tasks, causing 100% of live requests to timeout while 100% of SQLite write I/O is consumed by dead requests.
  * **Recommendation:**
    1. Enforce bounded queue depth: `queue.Queue(maxsize=1000)`.
    2. Apply backpressure on enqueue: reject immediately with a typed error or block with a bounded enqueue timeout:
       ```python
       try:
           self.queue.put((deadline, query, params, response_queue), timeout=ENQUEUE_TIMEOUT_SECONDS)
       except queue.Full:
           return False, BufferError("SerializedWriteQueue is saturated; write rejected under backpressure.")
       ```
    3. Include monotonic deadline in the task tuple. In `_worker_loop`, check `if time.perf_counter() > deadline` before executing; drop expired tasks immediately and notify the caller queue (or skip if already abandoned).

### Finding 3: Incomplete Batch & Shutdown Queue Drainage Leaking Orphaned Tasks
* **Severity:** Major
* **Affected Scope:** `interface/queue_writer.py:107-163`, `170-177` (`run()`, `_fail_all_pending()`, `_execute_single()`)
* **Finding & Recommendation:**
  * **Flaw:**
    1. In `run()`, when opportunistic auto-batching runs (`batch = [task] ... batch.append(next_item)`), up to 50 items are dequeued from `self.queue`. If an unhandled exception or non-catchable error occurs during `_execute_batch` (e.g. if `conn.rollback()` fails or memory error occurs), execution jumps to `except Exception as loop_error:` and calls `self._fail_all_pending(loop_error)`.
    2. Crucially, `_fail_all_pending` only inspects `self.queue.get_nowait()`. The items currently in `batch` were already removed from `self.queue`! None of the tasks in `batch` receive an error tuple in their `response_queue`. Their callers hang until `is_alive()` goes false, and their error is masked as a generic `RuntimeError("worker thread died")` rather than the underlying exception.
    3. In `_execute_single` (lines 174–176):
       ```python
       except Exception as e:
           conn.rollback()
           response_queue.put((False, e))
       ```
       If `conn.rollback()` raises (e.g. disk I/O failure, locked database, or corrupt transaction state), `response_queue.put` is bypassed, escaping directly to `run()` and crashing the entire worker.
    4. On graceful shutdown sentinel (`task is None`), the loop executes `break`. In normal termination, `_fail_all_pending` is never called. Any tasks enqueued concurrently right after `None` are abandoned in `self.queue` without notification.
  * **Recommendation:**
    1. Pass `batch` into failure drainage: `self._fail_batch(batch, loop_error)` prior to `self._fail_all_pending(loop_error)`.
    2. Defensively wrap rollback in `_execute_single`:
       ```python
       except Exception as e:
           try:
               conn.rollback()
           except Exception as rb_err:
               logger.warning("Defensive rollback failed: %s", rb_err)
           response_queue.put((False, e))
       ```
    3. Drain residual tasks in `self.queue` with `RuntimeError("SerializedWriteQueue shut down.")` upon receiving `None`.

### Finding 4: Fragile Worker Lifecycle: Inheriting `threading.Thread` Prevents Auto-Restart and Lacks Supervision
* **Severity:** Major
* **Affected Scope:** `interface/queue_writer.py:41`, `51-59`, `232-234` (`SerializedWriteQueue`, `execute_write`)
* **Finding & Recommendation:**
  * **Flaw:** `SerializedWriteQueue` inherits directly from `threading.Thread`. In Python, a `Thread` instance is strictly single-use; once `run()` exits, calling `.start()` again raises `RuntimeError("threads can only be started once")`.
  * **Architectural Risk:** There is no supervisor, health check, or auto-restart mechanism (`_ensure_worker_running()` does not exist). If the worker terminates due to transient disk contention, exhausted retries, or an unhandled exception, the queue instance is permanently dead. Every subsequent write will immediately fail with `RuntimeError("SerializedWriteQueue worker thread is not alive.")` until the entire process is restarted.
  * **Recommendation:**
    * Refactor `SerializedWriteQueue` from inheritance to composition:
      ```python
      class SerializedWriteQueue:
          def __init__(self, db_path: str):
              self._thread: Optional[threading.Thread] = None
              self._lock = threading.Lock()
      ```
    * Implement an idempotent, lock-protected `_ensure_worker_running()` that checks if `self._thread is None or not self._thread.is_alive()`, re-clears `_ready`, and spawns a fresh worker thread.

### Finding 5: Architectural Multi-Writer Bypass and Contention from Reader PRAGMAs
* **Severity:** Major
* **Affected Scope:** `core/database.py:38-46`, `50-64`, `interface/mcp_server.py:155-163`, `storage/store.py:75-77`
* **Finding & Recommendation:**
  * **Flaw:** The claim in `interface/queue_writer.py:8` that it *"Completely eliminates 'database is locked' errors"* is invalidated by surrounding architectural side-channels:
    1. **Direct Connection Bypass:** In `interface/mcp_server.py:162`, `db_manager = ConciergeDatabaseManager(resolved_db_path)` is instantiated without passing `write_queue` (`write_queue=None`). Consequently, all writes from `AgnosticCheckpointer` and `GraphRAGEngine` in production bypass `SerializedWriteQueue` entirely and open direct ephemeral connections (`sqlite3.connect`) on worker threads.
    2. **Competing Write Queues:** `storage/store.py` utilizes a completely separate write queue implementation (`storage.connection.SerializedWriteQueue`), creating multiple distinct threads writing to the same SQLite database file simultaneously.
    3. **Reader PRAGMA Contention:** In `core/database.py:40`, `read_query()` executes `conn.execute("PRAGMA journal_mode=WAL;")` on EVERY read query. In SQLite, executing PRAGMAs that inspect or alter journal modes acquires internal database locks, creating artificial lock contention against the writer thread even during read-heavy workloads.
  * **Recommendation:**
    1. Unify the write queue into a single canonical singleton shared across `SqliteStore`, `ConciergeDatabaseManager`, and `AgnosticCheckpointer`.
    2. Explicitly wire `write_queue` in `interface/mcp_server.py`.
    3. Remove `PRAGMA journal_mode=WAL;` from `read_query()`. Setting WAL mode is a one-time schema initialization task, not a per-query read operation.

### Finding 6: Non-Idiomatic SQLite Transaction State and Python 3.12+ Compatibility in `_execute_batch`
* **Severity:** Nit
* **Affected Scope:** `interface/queue_writer.py:65`, `186`, `193` (`sqlite3.connect`, `_execute_batch`)
* **Finding & Recommendation:**
  * **Flaw:** `sqlite3.connect` does not set `autocommit=True` or `isolation_level=None`. Manually executing `conn.execute("BEGIN IMMEDIATE;")` alongside Python's implicit transaction manager triggers `OperationalError: cannot start a transaction within a transaction` in Python 3.12+ if previous DML statements left implicit transactions uncommitted. Furthermore, `_execute_single` returns only `cursor.lastrowid`, discarding `rowcount` and breaking SQL queries utilizing `RETURNING` clauses.
  * **Recommendation:**
    * Explicitly set `isolation_level=None` (or `autocommit=True` on Python 3.12+) to control transaction boundaries strictly through explicit SQL commands.
    * Return a richer execution result tuple (e.g. `(True, {"lastrowid": cursor.lastrowid, "rowcount": cursor.rowcount})`).
