A.1 ConnectionManager.close() só fecha conexão da THREAD ATUAL
----------------------------------------------------------------------

LOCALIZAÇÃO:    storage/connection.py:238-249

O QUE É:
    O método close() do ConnectionManager para a fila de escrita mas fecha
    apenas a conexão de LEITURA da THREAD ATUAL (via threading.local()).

    CÓDIGO ATUAL (não corrigido):
        def close(self) -> None:
            self._write_queue.stop()
            conn = getattr(self._local, "conn", None)
            if conn:
                conn.close()
                self._local.conn = None

    Isso fecha apenas a conexão da thread que chamou close(). Outras threads
    que tenham obtido conexões de leitura via get_read_connection() terão
    suas conexões vazadas (nunca fechadas).

POR QUE NÃO FOI CORRIGIDO:
    A prioridade foi dada às issues de funcionalidade (órfãos, bugs).
    Esta issue é um vazamento de recurso que só afeta cenários multi-thread
    com criação/destruição frequente de threads.

IMPACTO:
    - Em cenários multi-thread (ex: Janitor rodando em background), as
      conexões de leitura de threads auxiliares não são fechadas no shutdown
    - Vazamento de file descriptors em execução prolongada
    - No uso atual (poucas threads estáveis), o impacto é baixo

COMO CORRIGIR:
    Manter um registro de TODAS as conexões de leitura criadas:
    1. Usar um dict thread_id → connection em vez de threading.local()
    2. No close(), iterar sobre TODAS as conexões e fechá-las
    3. Em get_read_connection(), registrar a conexão no dict

    Alternativa: usar weakref.WeakValueDictionary para evitar memory leak
    das conexões de threads já destruídas.

    Arquivo: storage/connection.py (linhas 238-249 e 251-280)


A.2 Qdrant NO-OP permanente (sem retry/backoff)
----------------------------------------------------------------------

LOCALIZAÇÃO:    core/vector_backend.py:52-72

O QUE É:
    Se o Qdrant estiver fora do ar no momento da inicialização, ou se o
    pacote qdrant-client não estiver instalado, o QdrantVectorStore entra
    em modo NO-OP PERMANENTE:

        if not self._available:
            self._client = None
            return

    Depois que o Qdrant volta ou o pacote é instalado, o store continua
    em NO-OP. Não há tentativa de reconexão periódica.

CÓDIGO ATUAL (não corrigido):
    def __init__(self, ...):
        self._available = QDRANT_AVAILABLE
        ...
        if not self._available:
            logger.warning("QdrantVectorStore operando em modo NO-OP...")
            self._client = None
            return
        # Só tenta conectar se available for True na inicialização
        ...

POR QUE NÃO FOI CORRIGIDO:
    O ChromaDB é o backend padrão e mais usado. O Qdrant é alternativo.
    A correção foi considerada de baixa prioridade.

IMPACTO:
    - Se o Qdrant cair temporariamente (reinicialização do container, rede),
      todas as operações vetoriais ficam mudas até o próximo restart do
      Grafo Concierge
    - A mensagem de erro é apenas um log warning — operação silenciosamente
      degradada (buscas semânticas retornam vazias)

COMO CORRIGIR:
    Implementar reconexão com backoff:
    1. Substituir _available por um método _ensure_connected() que tenta
       reconectar antes de cada operação (search, store_embedding, delete)
    2. Usar exponential backoff (1s, 2s, 4s, 8s, max 60s)
    3. Se reconectar com sucesso, _available = True e limpar o warning

    Passos:
    a) Renomear _available → _connected (bool)
    b) Criar _ensure_connected():
         if self._connected:
             return True
         try:
             self._client = qdrant_client.QdrantClient(...)
             self._ensure_collection(self._collection_name)
             self._connected = True
             logger.info("Qdrant reconectado com sucesso.")
             return True
         except Exception as e:
             logger.warning("Falha na reconexão Qdrant: %s", e)
             return False
    c) Chamar _ensure_connected() no início de search(), store_embedding(),
       delete_embedding()

    Arquivo: core/vector_backend.py (múltiplos métodos: __init__, search,
             store_embedding, delete)


A.3 JOIN desnecessário com nodes_fts em detect_communities
----------------------------------------------------------------------

LOCALIZAÇÃO:    services/janitor.py:470-481 (query SQL)

O QUE É:
    A query para detectar super-nós (nós com in_degree >= threshold) faz
    um JOIN com a tabela virtual nodes_fts (FTS5) que não é usado em
    lugar nenhum:

    CÓDIGO ATUAL (não corrigido):
        SELECT n.id
        FROM nodes n
        JOIN nodes_fts f ON n.id = f.rowid      ← JOIN DESNECESSÁRIO
        LEFT JOIN edges e ON n.id = e.target_id
        WHERE n.project_uuid = ? AND n.status = 'ACTIVE'
        GROUP BY n.id
        HAVING COUNT(e.source_id) >= ?

    O JOIN com nodes_fts não é referenciado no WHERE, SELECT nem HAVING.
    A query funcionaria identicamente sem ele.

POR QUE NÃO FOI CORRIGIDO:
    Provavelmente esquecido por ser um problema de performance menor
    que não afeta a correção dos dados.

IMPACTO:
    - Performance ligeiramente degradada: o SQLite precisa fazer o JOIN
      com a tabela virtual FTS5, que envolve overhead de indexação
    - Em projetos com muitos nós, pode causar slowdown perceptível no
      Janitor durante a detecção de comunidades

COMO CORRIGIR:
    Remover a linha JOIN nodes_fts:

        SELECT n.id
        FROM nodes n
        LEFT JOIN edges e ON n.id = e.target_id
        WHERE n.project_uuid = ? AND n.status = 'ACTIVE'
        GROUP BY n.id
        HAVING COUNT(e.source_id) >= ?

    Arquivo: services/janitor.py (linhas 470-481)


A.4 Prompt Armor com tag XML inventada
----------------------------------------------------------------------

LOCALIZAÇÃO:    ingestion/parser.py:36-37

O QUE É:
    O Prompt Armor envolve chunks de código em tags XML inventadas pelo
    desenvolvedor:

    CÓDIGO ATUAL (não corrigido):
        PROMPT_ARMOR_OPEN: str = "<raw_data_do_not_execute>"
        PROMPT_ARMOR_CLOSE: str = "</raw_data_do_not_execute>"

    Esta tag NÃO é um padrão conhecido (como <system>, <human> ou <tool>).
    LLMs podem ou não respeitar essa tag consistentemente — não há
    garantia de que o modelo entenda que o conteúdo não deve ser executado.

POR QUE NÃO FOI CORRIGIDO:
    O sistema funciona com LLMs que respeitam a tag (Gemini, Claude).
    A correção foi considerada cosmética/de segurança.

IMPACTO:
    - Proteção não confiável: alguns LLMs podem executar ou ignorar
      código nessas tags
    - Falsa sensação de segurança
    - Se um provedor de LLM mudar o comportamento, chunks de código
      podem vazar para execução

COMO CORRIGIR:
    Opção A: Usar XML comments (<!-- -->) ou tags específicas do
        provedor (ex: <ant:artifact> para Anthropic)
    Opção B (recomendada): Substituir por sanitização real:
        - Escapar caracteres especiais (< → &lt;, etc.)
        - Remover backticks do conteúdo
        - Substituir a tag por um marcador COMMENT padrão

    Arquivo: ingestion/parser.py (linhas 36-37 e método _armor_content
             na linha ~925)

B.1 chunk._node_id dinâmico — dataclass corrigida mas código ainda usa underscore
----------------------------------------------------------------------

LOCALIZAÇÃO:
    - ingestion/parser.py:72 (dataclass ParsedChunk — CORRIGIDO)
    - ingestion/orchestrator.py:397 (escrita — AINDA USA UNDERSCORE)
    - ingestion/orchestrator.py:530 (leitura — AINDA USA UNDERSCORE)

O PROBLEMA ORIGINAL:
    O IngestionManager._step_store_sqlite() fazia:
        chunk._node_id = chunk_node_ids[i]
    onde _node_id NÃO era um campo da dataclass ParsedChunk.

    A dataclass NÃO tinha campo node_id — o atributo era adicionado
    dinamicamente, violando o contrato da dataclass.

O QUE FOI CORRIGIDO:
    ✅ parser.py:72 — A dataclass ParsedChunk agora declara:
        node_id: Optional[int] = None

O QUE AINDA ESTÁ ERRADO:
    ❌ orchestrator.py:397 — AINDA usa underscore + type: ignore:
        chunk._node_id = chunk_node_ids[i]  # type: ignore[attr-defined]

    ❌ orchestrator.py:530 — AINDA lê com getattr + underscore:
        node_id = getattr(chunk, "_node_id", None)

IMPACTO:
    - O campo correto (node_id) é declarado mas NUNCA é populado
    - O campo errado (_node_id) continua sendo setado dinamicamente
    - O # type: ignore[attr-defined] no código indica que o desenvolvedor
      sabia do problema mas não o corrigiu completamente
    - Se a dataclass for congelada (frozen=True), o código quebra

COMO CORRIGIR (simples — 2 linhas):

    1. orchestrator.py:397
        DE:  chunk._node_id = chunk_node_ids[i]  # type: ignore[attr-defined]
        PARA: chunk.node_id = chunk_node_ids[i]

    2. orchestrator.py:530
        DE:  node_id = getattr(chunk, "_node_id", None)
        PARA: node_id = chunk.node_id

    Arquivos:
    - ingestion/orchestrator.py (linhas 397 e 530)

C.1 middleware.py acessa self._store._conn_mgr.write() diretamente
----------------------------------------------------------------------

LOCALIZAÇÃO:    core/middleware.py:616

O QUE É:
    O método update_fact_utility() da Fachada Central acessa o atributo
    PRIVADO _conn_mgr do SqliteStore diretamente:

    CÓDIGO:
        def update_fact_utility(self, fact_id: int, was_useful: bool) -> None:
            from storage.semantic_logic import update_memory_utility

            def _do_update(conn) -> None:
                update_memory_utility(conn, fact_id, was_useful)

            self._store._conn_mgr.write(_do_update)   # ← PRIVATE ACCESS

POR QUE ISSO É UM PROBLEMA:
    O SqliteStore encapsula o ConnectionManager como _conn_mgr (privado).
    O middleware (que deveria usar apenas a API pública do store) está
    acessando um atributo privado.

    Isso é uma violação de encapsulamento IGUAL à que foi corrigida no
    Janitor (issue 3.2 original): o Janitor acessava
    self._store._conn_mgr._write_queue._queue.empty() e foi corrigido
    com self._store.is_write_queue_empty().

    Aqui, o mesmo padrão foi reintroduzido — em vez de criar um método
    público no SqliteStore (ex: execute_write_operation()), o middleware
    acessa _conn_mgr diretamente.

IMPACTO:
    - Se _conn_mgr for renomeado (refatoração), update_fact_utility quebra
    - Inconsistência: o store tem is_write_queue_empty() público mas não
      tem um método genérico de escrita
    - Violação do princípio de encapsulamento

COMO CORRIGIR:
    Opção A (recomendada — mais limpa):
        Adicionar método público em SqliteStore:
            def write_callback(self, fn: Callable, *args, **kwargs) -> Any:
                return self._conn_mgr.write(fn, *args, **kwargs)

        Substituir em middleware.py:616:
            DE:  self._store._conn_mgr.write(_do_update)
            PARA: self._store.write_callback(_do_update)

    Opção B (mínima):
        Adicionar método específico update_fact_utility no SqliteStore
        que encapsula a chamada ao sematic_logic.update_memory_utility().

    Arquivos a modificar:
    - storage/store.py (adicionar write_callback ou update_fact_utility)
    - core/middleware.py (linha 616: substituir acesso direto)
