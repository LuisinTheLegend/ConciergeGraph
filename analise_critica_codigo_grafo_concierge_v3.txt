1.1 Qdrant NO-OP permanente (sem retry/backoff)
----------------------------------------------------------------------

LOCALIZAÇÃO:    core/vector_backend.py:52-72

O QUE É:
    Se o Qdrant estiver fora do ar no momento da inicialização, ou se o
    pacote qdrant-client não estiver instalado, o QdrantVectorStore entra
    em modo NO-OP PERMANENTE.

    CÓDIGO ATUAL (não corrigido):
        def __init__(self, ...):
            self._available = QDRANT_AVAILABLE
            ...
            if not self._available:
                logger.warning("QdrantVectorStore operando em modo NO-OP...")
                self._client = None
                return
            # Só tenta conectar se available for True na inicialização
            ...

    Todos os métodos (store_embedding, search, delete, etc.) verificam:
        if not self._available or not self._client:
            self._log_noop_warning()
            return  # ou return [], return 0

    Depois que o Qdrant volta ou o pacote é instalado, o store continua
    em NO-OP. Não há _ensure_connected(), nem reconexão periódica, nem
    exponential backoff.

    CÓDIGO AFETADO (todos os métodos que checkam NO-OP):
        - store_embedding()       → linha 141
        - store_embeddings_batch() → linha 161
        - search()                → linha 205
        - delete()                → linha ~270
        - verify_sync()           → linha ~300

POR QUE OCORRE:
    O desenvolvedor assumiu que a disponibilidade do Qdrant é estática
    (verificada apenas no __init__). Em ambientes reais (Docker, k8s),
    o Qdrant pode reiniciar ou a rede pode falhar temporariamente.

IMPACTO:
    - Se o Qdrant cair temporariamente, todas as operações vetoriais
      ficam mudas até o próximo restart do Grafo Concierge
    - A mensagem de erro é apenas um log warning com rate-limit de 5s
      — operação silenciosamente degradada
    - Buscas semânticas retornam vazias sem que o usuário perceba o motivo
    - Em produção com Qdrant como backend, isso é CRÍTICO

COMO CORRIGIR:

    Passo 1: Renomear flag e adicionar método de reconexão
        DE:  self._available = QDRANT_AVAILABLE
        PARA: self._connected = QDRANT_AVAILABLE

        Adicionar método:
        def _ensure_connected(self) -> bool:
            if self._connected and self._client:
                return True
            try:
                from qdrant_client import QdrantClient as _QC
                self._client = _QC(
                    url=self._url,
                    location=self._location,
                    memory=self._memory,
                )
                self._ensure_collection(self._collection_name)
                self._ensure_collection("episodic_memory")
                self._connected = True
                logger.info("Qdrant reconectado com sucesso.")
                return True
            except Exception as e:
                logger.warning("Falha na reconexão Qdrant: %s", e)
                self._connected = False
                self._client = None
                return False

    Passo 2: Substituir checks NO-OP por _ensure_connected()
        Em store_embedding(), search(), delete(), verify_sync(), etc.:
            DE:  if not self._available or not self._client:
                     self._log_noop_warning()
                     return ...
            PARA: if not self._ensure_connected():
                      self._log_noop_warning()
                      return ...

    Passo 3: Adicionar exponential backoff (opcional, recomendado)
        import time
        self._backoff = 1.0      # começa em 1s
        self._max_backoff = 60.0 # máximo 60s

        Dentro de _ensure_connected(), se falhar:
            time.sleep(self._backoff)
            self._backoff = min(self._backoff * 2, self._max_backoff)
        Se conectar:
            self._backoff = 1.0  # reset

    Arquivo: core/vector_backend.py (múltiplos métodos)


1.2 Prompt Armor com tag XML inventada
----------------------------------------------------------------------

LOCALIZAÇÃO:    ingestion/parser.py:36-37

O QUE É:
    O Prompt Armor envolve chunks de código em tags XML inventadas pelo
    desenvolvedor para "proteger" o LLM de executar código:

    CÓDIGO ATUAL:
        PROMPT_ARMOR_OPEN: str = "<raw_data_do_not_execute>"
        PROMPT_ARMOR_CLOSE: str = "</raw_data_do_not_execute>"

    A tag é aplicada em _armor_content() (parser.py ~linha 925):
        def _armor_content(self, content: str) -> str:
            return f"{PROMPT_ARMOR_OPEN}\n{content}\n{PROMPT_ARMOR_CLOSE}"

    E usada em todos os métodos de parse (AST chunks, code chunks, etc.)
    para envolver o conteúdo antes de enviar ao LLM.

POR QUE OCORRE:
    O desenvolvedor inventou uma tag XML própria em vez de usar:
    - Padrões estabelecidos (ex: <system>, <human> do Anthropic)
    - Sanitização real (escapar caracteres, remover backticks)
    - XML comments (<!-- -->) que são ignorados por parsers XML

IMPACTO:
    - Proteção não confiável: não há garantia que o LLM entenda que o
      conteúdo dentro de <raw_data_do_not_execute> não deve ser executado
    - Diferentes provedores de LLM tratam tags desconhecidas de formas
      diferentes — alguns podem ignorar e tratar como conteúdo normal
    - Falsa sensação de segurança: o desenvolvedor acredita que o código
      está "armorado" quando na verdade a proteção é apenas uma convenção
      não padronizada

COMO CORRIGIR:

    Opção A (mínima): Substituir por XML comment
        PROMPT_ARMOR_OPEN: str = "<!-- DATA_DO_NOT_EXECUTE:"
        PROMPT_ARMOR_CLOSE: str = "-->"

        XML comments são padronizados e LLMs treinados em dados da web
        reconhecem que comments não são código executável.

    Opção B (recomendada): Sanitização real
        1. Escapar caracteres especiais:
           content = content.replace("&", "&amp;")
                            .replace("<", "&lt;")
                            .replace(">", "&gt;")
                            .replace("`", "\\`")
        2. Remover ou escapar backticks triplos (```) que delimitam
           blocos de código
        3. Substituir a tag XML por um cabeçalho COMMENT:
           "[[ SNIPPET DE CÓDIGO (NÃO EXECUTAR) ]]" (em maiúsculas
           para reforçar a instrução)

    Arquivo: ingestion/parser.py (linhas 36-37 e método _armor_content)

2.1 Classe ThompsonRetriever (código não chamado em produção)
----------------------------------------------------------------------

LOCALIZAÇÃO:    core/probabilistic_retriever.py (94 linhas)

O QUE É:
    A classe ThompsonRetriever implementa a lógica de Amostragem de
    Thompson para balancear exploração vs explotação na busca.

    O código é completo, testado (tests/_test_probabilistic_retriever.py)
    e funcional, mas NENHUM código de produção o instancia ou chama.

POR QUE É ÓRFÃO:
    A funcionalidade de Thompson Sampling foi implementada DIRETAMENTE
    no HybridSearchEngine._apply_thompson_sampling() (hybrid_search.py:218),
    que contém uma versão inline simplificada. A classe original
    ThompsonRetriever foi deixada para trás.

    A classe não é:
    - Exportada em core/__init__.py
    - Instanciada em core/middleware.py (Fachada Central)
    - Referenciada em core/hybrid_search.py

IMPACTO:
    - Código morto: 94 linhas que nunca executam em produção
    - Manutenção duplicada: se a lógica de Thompson Sampling mudar,
      é preciso atualizar tanto a classe quanto o método inline
    - Confusão para novos desenvolvedores: duas implementações da
      mesma coisa, uma delas sem uso

COMO CORRIGIR:

    Opção A (recomendada): Delegar para a classe ThompsonRetriever
        1. Refatorar HybridSearchEngine._apply_thompson_sampling() para
           instanciar e chamar ThompsonRetriever.retrieve()
        2. Exportar ThompsonRetriever em core/__init__.py

    Opção B (mínima): Remover a classe
        1. Mover o conteúdo para um arquivo de arquivo histórico
        2. Ou simplesmente deletar probabilistic_retriever.py e seu teste

    Arquivos:
    - core/probabilistic_retriever.py (94 linhas)
    - core/hybrid_search.py (linhas 218-246)
    - core/__init__.py (export ou remoção)


2.2 Coleção episodic_memory (criada mas nunca populada)
----------------------------------------------------------------------

LOCALIZAÇÃO:    core/vector_backend.py:78

O QUE É:
    O QdrantVectorStore.__init__() cria automaticamente uma coleção
    separada chamada "episodic_memory" para armazenar histórico
    conversacional episódico:

        self._ensure_collection("episodic_memory")

    E define validação de payload específica (linhas 109-122):
        required = ["scope_type", "scope_id", "timestamp",
                     "utility_alpha", "utility_beta"]

POR QUE É ÓRFÃO:
    NENHUM código de produção escreve na coleção episodic_memory:
    - O SemanticExtractor escreve apenas na tabela SQLite semantic_facts
    - O user_core_memory escreve apenas na tabela SQLite user_core_memory
    - O concierge_store_fact MCP tool escreve apenas no SQLite
    - Não há hook que sincronize fatos semânticos com a coleção vetorial

IMPACTO:
    - A coleção é criada mas jamais recebe dados
    - A validação de payload existe mas nunca é acionada por INSERTs reais
    - O diferencial de "memória episódica conversacional separada da
      memória de código" não é entregue

COMO CORRIGIR:
    Depende da integração com SemanticExtractor:
    1. No método store_fact() da Fachada Central (middleware.py:506),
       após salvar no SQLite, também armazenar um embedding na coleção
       episodic_memory do QdrantVectorStore (ou chroma equivalente)
    2. Criar um método público no GrafoConcierge para sync semântico
    3. Ou criar um serviço background (similar ao Janitor) que faz o
       sync periódico entre SQLite semântico e vector store episódico

    Nota: Isso só é relevante se o backend for Qdrant (ChromaDB não
    suporta coleções múltiplas da mesma forma).

    Arquivos:
    - core/middleware.py (store_fact: adicionar escrita vetorial)
    - core/vector_backend.py (verificar se método público existe)
