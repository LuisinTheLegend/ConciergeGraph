PARTE 1 — AVALIAÇÃO GERAL
O Grafo Concierge é um projeto ambiciosos e, nas partes que foram implementadas, revela qualidade técnica real. A arquitetura da storage layer é sofisticada, o pipeline de ingestão é resiliente, e o design de concorrência resolve um problema real (SQLite sob carga concorrente com MCP Server vs Janitor). Porém, o projeto carrega um gap severo entre o que está documentado e o que existe em código. A versão 3.8.0 se autodenomina "Absolute Solidity" mas está longe de ser sólida em vários eixos críticos. A análise abaixo é dividida em três grandes blocos: o que foi implementado (e como está), o que foi prometido (e o que falta), e os problemas concretos encontrados.

PARTE 2 — O QUE FOI IMPLEMENTADO E COMO ESTÁ
2.1 Storage Layer (storage/)
A camada de armazenamento é, de longe, o módulo mais bem-executado do projeto. Cada componente tem responsabilidade clara e as decisões técnicas são apropriadas para o contexto de uso.
2.1.1 connection.py — Gerenciamento de Conexões
A classe ConnectionManager implementa uma separação leitura/escrita que é correta para SQLite:
- Leituras usam conexões thread-local (via threading.local), uma por thread, sem contenção entre threads.
- Escritas são delegadas a uma SerializedWriteQueue com thread dedicada (sqlite-writer).
- O PRAGMA journal_mode=WAL e busy_timeout=5000 são aplicados em todas as conexões.
- A fila de escrita usa um queue.Queue com sentinel value para terminação limpa.
- O contextmanager read() facilita o uso sem vazamento de conexões.
A implementação de _WriteJob como dataclass encapsulando callable + argumentos + result event é uma escolha de design elegante. O chamador bloqueia com job.result_event.wait() e a exceção é propagada corretamente com job.error. Isso elimina o erro "database is locked" em cenários de escrita concorrente — um problema real que o SQLite tem por padrão.
Nota positiva: o worker thread configura a conexão antes de entrar no loop e fecha no finally, garantindo que não há vazamento de conexão mesmo em erros.
2.1.2 schema.py — Definição do Schema
O SchemaManager aplica o schema de forma idempotente:
- 6 tabelas (projects, nodes, edges, reference_wings, trajectories, commit_log) com CHECK constraints inline.
- 10 índices para performance.
- Tabela virtual FTS5 com sincronização via triggers (nodes_ai, nodes_ad, nodes_au).
- Versionamento do schema via PRAGMA user_version com conversão semântica (3.8.0 → 308000).
- Verificação de tabelas e triggers após aplicação.
A abordagem de criar tudo com IF NOT EXISTS e verificar depois é robusta para inicialização repetida. O rebuild do FTS5 via INSERT INTO nodes_fts(nodes_fts) VALUES('rebuild') é documentado para grandes cargas.
2.1.3 store.py — SqliteStore (Fachada)
A fachada SqliteStore é bem organizada e expõe uma API limpa para todos os módulos:
- CRUD completo de projects, nodes, edges, trajectories, commits, reference_wings.
- Validação de enums (VALID_NODE_TYPES, VALID_PRIVACY_LEVELS, VALID_STATUSES) antes de cada escrita.
- Lookup por UUID ou folder_name em get_project() — conveniente para CLI.
- O padrão de delegar operações de inteligência para GraphLogic é limpo.
Métodos noteworthy:
- find_node_by_hash() — suporta delta detection corretamente.
- touch_node_commit() — atualiza last_commit_at para cálculo de recência.
- bulk_decay_stale_trajectories() — batch operation para o Janitor.
2.1.4 logic.py — Motor de Inteligência
O GraphLogic implementa os três pilares de inteligência:
1. Decaimento de Trajetórias — máquina de estados finitos (ACTIVE ↔ STALE ↔ ARCHIVED) com transições validadas. A transição ARCHIVED → qualquer é terminal e rejeitada. A transição STALE → ACTIVE é permitida (re-ativação). Implementação correta.
2. Centralidade — min(in_degree / 10, 1.0). Nós com 10+ dependentes são "Super-Nós" com centralidade máxima. A normalização protege código core estável.
3. Score de Recência — decaimento exponencial e^(-λ × t) com λ = ln(2)/7 ≈ 0.0990 e meia-vida de 7 dias. Score mínimo de 0.01 garante que nós antigos nunca são zerados.
4. Busca Híbrida Ponderada — 0.50 × vetorial + 0.25 × FTS5 + 0.25 × max(recência, centralidade). A versão batch (compute_centrality_batch e compute_recency_batch) faz 2 queries SQL para N candidatos, em vez de 2N — otimização importante.
5. CTE Recursivas — árvores de dependências com limite de profundidade 10, proteção anti-loop, e versões source→target e target→source.
Crítica pontual: O cálculo de decaimento em _calculate_decay usa datetime.utcnow() mas o campo last_commit_at é gravado em datetime.utcnow().strftime(...) (store.py:268) — formato ISO sem timezone. A comparação com datetime.fromisoformat funciona se os formatos coincidirem, mas há risco sutil se o SO tiver timezone diferente ou se SQLite gravar em formato diferente. Não é um bug concreto, mas é frágil.
2.1.5 vector_store.py — ChromaDB + EmbeddingManager
O ChromaVectorStore implementa corretamente a interface BaseVectorBackend:
- Lazy loading do ChromaDB com import defensivo.
- store_embeddings_batch com chunking de BATCH_SIZE=100 para evitar OOM.
- search() retorna VectorSearchResult com score já normalizado (1 - distance).
- _build_where_filter monta filtros corretos para ChromaDB ($in para múltiplos UUIDs).
- verify_sync() detecta órfãos comparando IDs do ChromaDB com IDs válidos do SQLite.
O EmbeddingManager suporta model tiering (FLASH/ELITE) com lazy loading do modelo. O Semantic Fallback retorna None em vez de propagar erro, permitindo que o pipeline continue mesmo com falhas de embedding.

2.2 Ingestion Layer (ingestion/)
2.2.1 crawler.py — Varredura de Filesystem
O ProjectCrawler é bem implementado:
- SHA256 em blocos de 64KB (eficiente para arquivos grandes).
- Delta detection via find_node_by_hash() no SQLite.
- .gitignore parsing com suporte a padrões glob, negação (!), diretórios (dir/), e ** recursivo.
- Classificação por extensão com 30+ mapeamentos (code, doc, config, conversation).
- Detecção de nós órfãos para GC (só nós do tipo 'file').
- Diretórios ocultos filtrados exceto exceçõesallowlist.
- Limite de 10MB por arquivo.
A segurança no GC (só deletar tipo='file') é correta — diretórios, clusters e project nodes nunca são deletados por esta rotina.
2.2.2 parser.py — Semantic/AST Chunking
O FileParser implementa chunking inteligente:
- Python: usa ast (stdlib) para extrair funções, classes, e módulo com linhas corretas.
- JS/TS: regex para detectar classes e funções (incluindo arrow functions e async).
- Markdown: chunking por headers (#).
- Config: chunk único respeitando limite de tokens.
- RAW: fallback por tamanho fixo.
- _split_oversized() subdivide chunks que excedem MAX_CHUNK_TOKENS (512).
Prompt Armor envolvendo conteúdo em <raw_data_do_not_execute>...</raw_data_do_not_execute> é uma defesa correta contra prompt injection.
Detecção de tags via regex de imports (Python e JS/TS) e palavras-chave de frameworks. A lista HIGH_PRIORITY_TAGS em summarizer.py e _FRAMEWORK_KEYWORDS em parser.py têm sobreposição —DRY violado.
2.2.3 summarizer.py — Zoom Summarizer
O ZoomSummarizer implementa a Engrenagem de Zoom (L0/L1/L2):
- L0: resumo de chunk individual (MAX 150 tokens).
- L1: síntese de cluster (L0s agrupados por diretório) — MAX 300 tokens.
- L2: Bússola de Contexto global (L1s consolidados) — MAX 300 tokens.
O Retry Loop com Heuristic Fallback é implementado em 3 níveis:
1. json.loads() direto.
2. Regex _JSON_BLOCK_RE para extrair JSON embutido.
3. Extração via find("{") / rfind("}").
4. Fallback: Dumb Summary (texto plano truncado).
A Amnésia Seletiva (_prune_low_relevance) remove módulos com relevance_score < 0.15 no L2, mas garante pelo menos 1 resultado (top-1).
O LLMAdapter tenta Gemini → OpenAI como fallback. O adapter aceita call_fn customizada para testes, o que é prático.
2.2.4 orchestrator.py — IngestionManager
O IngestionManager orquestra o pipeline completo de 7 etapas:
1. CRAWL → 2. PARSE → 3. SUMMARIZE → 4. STORE SQLite → 5. EMBED → 6. STORE Vector → 7. GC
O short-circuit quando não há mudanças (new_files e deleted_node_ids vazios) é uma otimização inteligente.
A geração de arestas estruturais (diretório → chunk) é criada automaticamente.
O generate_project_context() constrói clusters L1 a partir de resumos L0 existentes no SQLite e gera L2 via ZoomSummarizer.

2.3 Services (services/)
janitor.py — Background Janitor
O JanitorService implementa 5 etapas de manutenção:
1. Decaimento de trajetórias stale (> 30d).
2. Sincronização SQLite ↔ ChromaDB ( Reconciliation Loop).
3. Arquivamento de nós inativos (> 60d sem acesso).
4. Auto-Zoom (L1/L2) se threshold de 10+ mudanças.
5. FTS Rebuild após mudanças.
O Idle-Lock (signal_mine_start/end, _wait_for_idle) é a heurística correta: se mine() está rodando, o Janitor adia operações destrutivas. O timeout de 30s (IDLE_LOCK_TIMEOUT) é razoável.
Suporte a background thread com start_background() / stop_background() e daemon=True para não bloquear shutdown.

2.4 Server (server/)
mcp_server.py — GrafoConciergeServer
O servidor FastMCP expõe 3 tools com handlers bem estruturados:
- concierge_mine: cria/procura projeto + executa IngestionManager.mine() + Idle-Lock signaling.
- concierge_search: pipeline de busca híbrida completo (vetorial → FTS5 → merge → hybrid score → enriquecimento).

O handler de search é particularmente bemfeito: over-fetch de 2x no vetorial para reranking, merge de candidatos exclusivos do FTS, e enriquecimento com dados completos do nó.

PARTE 4 — BUGS E PROBLEMAS CONCRETOS
4.1 Bug de Tipo em verify_sync — CRÍTICO
Arquivo: storage/vector_store.py:494-537
Arquivo que usa: ingestion/orchestrator.py:426-434
Severidade: ALTA
O método verify_sync em vector_store.py foi declarado e implementado como retornando list[str] (lista de doc_ids órfãos):
def verify_sync(self, sqlite_node_ids: set[int]) -> list[str]:
    ...
    return orphans  # orphans é list[str]
Porém, em orchestrator.py, o código tenta tratar o retorno como dict:
sync_report = self._vector.verify_sync(sqlite_ids)
orphan_count = sync_report.get("orphans_removed", 0)  # TypeError!
list não tem método .get(). Isso vai lançar AttributeError em tempo de execução após qualquer operação de GC. O campo orphans_removed também é inventado — o método não retorna um dict com esse campo.
Impacto: toda vez que uma limpeza pós-GC é tentada, o pipeline falha silenciosamente (logged como debug) e o Reconciliation Loop não funciona. Vetores órfãos se acumulam no ChromaDB.
4.2 FTS5 Injection Potential — MÉDIA
Arquivo: storage/logic.py:369-386
Severidade: MÉDIA
O método fts_search em logic.py recebe node_type como parâmetro e o insere diretamente no SQL via placeholder:
if node_type:
    sql += " AND n.node_type = ?"
    params.append(node_type)
O campo node_type é aceito como string sem validação. A validação existe em store.py:179-180 mas fts_search não a chama:
# Validação existe em store.py (create_node):
if node_type not in VALID_NODE_TYPES:
    raise ValueError(f"node_type inválido: '{node_type}'")
# Mas fts_search em logic.py não valida:
def fts_search(..., node_type: Optional[str] = None, ...) -> list[dict]:
    if node_type:
        sql += " AND n.node_type = ?"  # ← concatenation direta
        params.append(node_type)
Se um node_type malicioso for passado (ex: 'FACT' OR 1=1 --), o SQL pode se comportar de forma inesperada. Para o FTS5 isso é menos grave do que SQL clássico (o FTS5 não permite subqueries convencionais), mas é uma má prática.
Fix necessário: adicionar validação if node_type and node_type not in VALID_NODE_TYPES: raise ValueError(...) no início de fts_search.
4.3 Janitor Não Deleta Vetores Órfãos — CRÍTICO
Arquivo: services/janitor.py:276-299
Severidade: ALTA
O método _sync_vectors detecta vetores órfãos mas o código tem uma falha lógica:
def _sync_vectors(self, project_uuid: str, report: MaintenanceReport) -> int:
    ...
    orphans = self._vector.verify_sync(valid_ids)
    if not orphans:
        logger.debug("Sync: nenhum vetor órfão detectado.")
        return 0
    # Remove orphans em batch
    removed = self._vector.delete_batch(orphans)
    logger.info("Sync: %d vetores órfãos removidos.", removed)
    return removed
Este código parece correto. Mas há um problema: em orchestrator.py:426-434, após o GC, o sistema tenta rodar um segundo Reconciliation Loop que falha por causa do bug 4.1. Além disso, não há retry se o primeiro delete falhar parcialmente.
O problema real: o _sync_vectors do Janitor chama verify_sync com um conjunto de IDs de nós ativos (status="ACTIVE"), mas não inclui nós recém-criados que ainda não têm embeddings armazenados. Se o pipeline mine() criou nós no SQLite mas falhou ao armazenar embeddings no ChromaDB (caso de embedding retornando None), esses nós estarão no SQLite sem correspondente no ChromaDB — e o Janitor não os detecta porque verify_sync detecta órfãos no ChromaDB (doc_ids sem node_id no SQLite), não órfãos no SQLite (node_ids sem doc_id no ChromaDB).
4.4 Tests Não São Executáveis via pytest
Arquivo: tests/*.py
Severidade: MÉDIA
Os arquivos de teste são scripts Python com asserts no corpo do módulo (estilo "script de validação"), não funções de teste estruturadas para pytest. Se você rodar pytest tests/, nenhum teste será descoberto porque não há funções test_*().
Exemplo em _test_orchestrator.py:
# Este código roda como SCRIPT (python tests/_test_orchestrator.py)
# Mas não é discoverível pelo pytest
assert result.files_processed == 4
print("  [PASS] Pipeline completo OK")
Isso impede:
- Execução via CI/CD (GitHub Actions, GitLab CI).
- Cobertura de código (pytest --cov).
- Test discovery automático.
4.5 LLMAdapter Não Suporta Anthropic
Arquivo: ingestion/summarizer.py:181-216
Severidade: BAIXA (contexto de uso)
O adapter implementa fallback na ordem: Gemini → OpenAI. Mas o projeto é arquitetado para integração com Claude Desktop via MCP. O Anthropic (claude-haiku para local inference) não é tentado. Se o usuário quiser usar um modelo diferente (Anthropic, Ollama, LM Studio local), não há mecanismo built-in.
Isso não é um bug — é uma limitação de design. A decisão de API é arbitrária (Gemini como default). A call_fn customizada mitiga isso, mas não é discoverível para o usuário comum que apenas configura GRAFO_LLM_API_KEY.
4.6 ZoomSummarizer Gera Dumb Summary como Fallback Final — MÉDIA
Arquivo: ingestion/summarizer.py:294-307
Severidade: MÉDIA
Se o LLM falhar 3 vezes na extração de JSON, o sistema grava um "Dumb Summary" — texto plano truncado prefixado com [DUMB]. Para um projeto que se auto-intitula "Infraestrutura de Memória Permanente para Agentes Autônomos", ter resumos "dumb" polui o contexto de busca e degrada a qualidade da LTM.
Não há:
- Notificação ao usuário de que o resumo é "dumb".
- Retry com backoff exponencial entre tentativas.
- Fallback para chamar um modelo mais capaz se o Flash falhar.
- Flag no nó que marque o resumo como não-confiável.
O campo is_dumb_summary existe no SummaryResult, mas não é persistido no SQLite (o campo status do nó só suporta ACTIVE/STALE/ARCHIVED).

O arquivo requirements.txt é binário (não-UTF8), impossibilitando que desenvolvedores vejam as dependências do projeto sem instalar. Isso é um blocker para onboarding.
4.8 Janitor.run_maintenance Não Deleta Vetores do ChromaDB Corretamente
Arquivo: services/janitor.py:283-291
Severidade: ALTA
O método _sync_vectors obtém valid_ids a partir de get_nodes_by_project(project_uuid, status="ACTIVE"), mas o método verify_sync da ChromaVectorStore retorna doc_ids (strings no formato node_{id}). A comparação de tipos pode falhar silenciosamente:
# Em janitor.py:
valid_ids: set[int] = {n["id"] for n in nodes}  # set[int]
# Em vector_store.py verify_sync:
for doc_id, meta in zip(all_ids, all_metas):
    node_id = meta.get("node_id")
    if int(node_id) not in sqlite_node_ids:
        orphans.append(doc_id)
O int(node_id) assume que meta.get("node_id") é sempre convertible para int. Se o metadata estiver corrompido (None ou string inválida), int(None) lança TypeError. O erro é capturado pelo except Exception e o loop continua, mas órfãos são perdidos.
4.9 Estrutura de Módulos Prometida Não Existe
Severidade: ALTA (para arquitetura futura)
A documentação descreve uma estrutura de diretórios com módulos (core/, agents/, interface/) que não existem. Isso significa que qualquer tentativa de estender o projeto seguindo a documentação vai falhar. Os nomes dos módulos internos estão descentralizados:
- GrafoConcierge (middleware/pseudo-core) deveria estar em core/middleware.py mas não existe.
- RevisorCritico deveria estar em agents/revisor_critico.py mas não existe.
- ActionGrafoHooks deveria estar em interface/action_hooks.py mas não existe.
O código existente está bem organizado nos módulos que foram criados (storage/, ingestion/, services/, server/), mas os módulos prometidos na arquitetura precisam ser criados para que o sistema seja extensível seguindo o plano original.
4.10 Janitor Não Atualiza last_accessed dos Nós
Arquivo: services/janitor.py
Severidade: BAIXA
O arquivamento de nós inativos em _archive_inactive_nodes verifica last_accessed para determinar se um nó está inativo. Porém, o sistema nunca atualiza last_accessed durante operações normais de busca. O campo existe no schema mas não é atualizado em nenhum lugar do código. Isso significa que last_accessed será sempre NULL e o arquivamento por inatividade nunca vai funcionar (sempre cai para updated_at ou created_at).

PARTE 5 — PROBLEMAS DE DOCUMENTAÇÃO
5.1 Versão "Absolute Solidity" é Prematura
A versão 3.8.0 se autodenomina "Absolute Solidity" mas tem bugs concretos (4.1, 4.3, 4.8), features prometidas não implementadas (4.1), e gaps severos entre docs e código (3.1). O nome "Absolute Solidity" passa uma impressão de completude que o código não sustenta. Um nome mais honesto seria "3.8.0 (Partial Implementation — Core Storage + Ingestion)".
5.2 Plano de Implementação Nunca Foi Executado
O documento PLANO_COMPLETO_GRAFO_CONCIERGE.md lista 6 fases com centenas de items marcados como [ ]. Isso sugere que o planejamento foi feito em detalhe mas nunca foi executado. Se o objetivo é completar o produto conforme especificado, é necessário um plano de execução real (Kanban, issues, milestones) em vez de um documento de especificação gigante.
5.3 Diferença de Nomenclatura entre Docs e Código
A documentação usa termos que não existem no código:
- "Bússola de Contexto" → implementado como summary na tabela projects (ok).
- "Ontologia Tipada" → o node_type existe e funciona (FACT, SKILL, INSIGHT, TRAJECTORY, PATCH).
- "Zoom Gear" → implementado parcialmente (ZoomSummarizer, mas não há ZoomGear como classe/conceito central).
- "Engrenagem de Zoom" → o mesmo que Zoom Gear.
- "Reconciliation Loop" → implementado em ChromaVectorStore.verify_sync().
- "Heurística de Idle-Lock" → implementado em JanitorService.
- "Amnésia Seletiva" → implementado em ZoomSummarizer._prune_low_relevance().
A nomenclatura técnica está parcialmente presente. Os termos mais importantes (Reconciliation Loop, Idle-Lock, Semantic Fallback, Strict Scoping) estão implementados e nomeados corretamente. Mas os conceitos mais abstratos ("Agente Soberano", "Memória Infinita", "Trajetórias Episódicas") são mais marketing do que implementação.
5.4 CHANGELOG.md Não Existe
O projeto não tem CHANGELOG. Para um sistema que se autodenomina "Absolute Solidity" e tem versão 3.8.0, é essencial ter registro do que mudou a cada versão.

PARTE 6 — PONTOS POSITIVOS INESPERADOS
6.1 Resiliência do Pipeline de Ingestão
O pipeline de ingestão (IngestionManager.mine()) é notavelmente resiliente. Cada etapa tem seu próprio try/except e não derruba o pipeline inteiro. O short-circuit quando não há mudanças é inteligente. O GC integrado é correto.
6.2 Arquitetura de Concorrência
A SerializedWriteQueue é uma solução elegante para um problema real. SQLite + MCP é uma combinação conhecida por causar "database is locked" e esta solução resolve isso sem necessidade de mudar para PostgreSQL ou outro banco.
6.3 AST Chunking para Python
Usar ast para chunking de Python é a escolha correta. Regex para Python é frágil; AST é robusto. A extração de linha начала e fim é precisa.
6.4 Testes Reais com Mocks Bem Definidos
Os testes usam componentes REAIS (SqliteStore, ChromaDB) com mocks pontuais apenas para componentes externos (LLM, EmbeddingManager). Isso é muito melhor do que mocks globais. O teste de stress (memory_stress_test.py) é um exercício completo de validação do ciclo de vida.
6.5 Model Tiering (EmbeddingManager)
A decisão de usar all-MiniLM-L6-v2 como default (local, gratuito, 384 dims) em vez de OpenAI (pago, 1536 dims) é financeiramente correta para um projeto de codebase indexing. O tiering FLASH/ELITE permite upgrade quando necessário.

PARTE 8 — CONCLUSÃO
O Grafo Concierge é um projeto com fundamentação técnica sólida na storage layer e no pipeline de ingestão. A arquitetura de concorrência (SerializedWriteQueue + WAL), o schema SQLite bem-definido (FTS5 + triggers + CHECK constraints), e o pipeline de ingestão em 7 etapas são implementasiões de alta qualidade que demonstram domínio técnico real.
O problema central é que o projeto se autodenomina completo ("Absolute Solidity") quando na verdade está parcialmente implementado. Das 7 ferramentas MCP prometidas, 4 não existem. Dos 15 módulos descritos na arquitetura, 10 não existem. Dos 6 fases do plano de implementação, 5 nunca foram executadas.
O gap entre documentação e código cria um risco severo de adoção: qualquer desenvolvedor que ler os docs e tentar usar o sistema vai encontrar uma versão muito menor do que o esperado. O sistema que existe é funcional e bem escrito para o que faz, mas precisa de honestidade sobre o estado atual do produto.
Recomendação final: mudar a versão para "3.8.0-alpha" ou "3.8.0 (Core + Ingestion Only)", focar nas 3 prioridades CRÍTICAS listadas acima, e criar um roadmap executável para chegar ao estado descrito na documentação. O código existente merece confiança; o labeling como "Absolute Solidity" não.
