5. DEPENDENCIA CRITICA DE LLM
================================================================================

O que e:
  Tres componentes principais dependem de chamadas a LLM para
  funcionar: SemanticExtractor (store_fact), ZoomSummarizer (L0/L1/L2)
  e Revisor Critico (auditoria/reranking). Se o LLM ficar indisponivel
  ou a chave expirar, esses componentes falham ou operam em modo
  degradado.

Localizacao:
  - memory_extractor.py:108 -> self.llm.generate(prompt, max_tokens=300)
  - summarizer.py: ~linha 200 (chamada LLM para cada nivel de resumo)
  - revisor_critico.py: ~linha 150 (chamada LLM para auditoria)
  - Configuracao: c:/Nexus-Memory/main.py:50-51
    LLM_MODEL = os.environ.get("GRAFO_LLM_MODEL", "gemini-2.0-flash")
    LLM_API_KEY = os.environ.get("GRAFO_LLM_API_KEY", "")

Por que ocorre:
  O design usa LLM como "cerebro" para tarefas de compreensao semantica
  (sumarizar, classificar fatos, auditar qualidade). Isso e intencional,
  mas cria single point of failure. Os fallbacks existem (dumb summary,
  ADD for store_fact, partial_audit) mas entregam qualidade inferior.

Impacto:
  - Se a API key expirar: store_fact retorna erro, summarizer gera
    "dumb summaries", revisor faz partial_audit sem validacao real
  - Se o modelo estiver sobrecarregado: latencia alta em todas as
    operacoes que envolvem LLM
  - Se o OpenRouter ficar fora do ar: sistema opera em modo degradado
  - Custo: cada mine(), store_fact() e commit() gasta tokens de LLM

Como corrigir (passo a passo):

  1. Implemente caching de respostas LLM:
     - Crie c:/Nexus-Memory/services/llm_cache.py
     - Use SQLite ou disco para cachear respostas de summarizacao
     - Invalide o cache quando o conteudo do arquivo mudar (file_hash)
     - Estime reducao de 40-60% nas chamadas LLM

  2. Adicione fallback entre modelos:
     - Edite c:/Nexus-Memory/ingestion/summarizer.py
     - Se o modelo primario falhar, tente um secundario:
       PRIMARY_MODEL = os.environ.get("GRAFO_LLM_MODEL", "gemini-2.0-flash")
       FALLBACK_MODEL = os.environ.get("GRAFO_LLM_FALLBACK", "openrouter/free")
     - Isso requer configurar GRAFO_LLM_FALLBACK_API_KEY tambem

  3. Adicione health check do LLM antes de operacoes:
     - Crie um metodo ping_llm() que faz uma chamada minimamente cara
       (ex: "Say 'ok'") e verifica se resposta e valida
     - Se o health check falhar, ative modo degraded com aviso no log

  4. Crie um modo "offline":
     - Sem LLM, use apenas FTS5 + similaridade de texto (TF-IDF)
       para buscas
     - Summarizer gera apenas "dumb summaries" (primeiros N caracteres)
     - store_fact sempre faz ADD (sem consolidacao semantica)
     - Revisor Critico sempre aprova com partial_audit=True

7. COLUNA "TYPE" AMBIGUA
================================================================================

O que e:
  A tabela nodes tem duas colunas de tipo: node_type (FACT, SKILL, ...)
  e type (default "file"). A semantica de "type" nao e clara — parece
  indicar a origem do no (veio de um arquivo) mas conflita com node_type.

Localizacao:
  c:/Nexus-Memory/storage/schema.py:71
    type          TEXT NOT NULL DEFAULT 'file',

  c:/Nexus-Memory/core/middleware.py:489
    "type": node["type"],

Por que ocorre:
  Provavelmente "type" foi criada primeiro para indicar a categoria
  do arquivo fonte (file, dir, symlink) e depois node_type foi
  adicionada para o tipo semantico. Mas a nomenclatura "type" e
  generica demais e causa confusao.

Impacto:
  - Desenvolvedores podem confundir type com node_type
  - Consultas SQL precisam de discriminacao explicita
  - A documentacao precisa explicar a diferenca sempre
  - Propenso a erros em codigo que le "type" esperando o tipo logico

Como corrigir (passo a passo):

  1. Renomeie a coluna no schema (opcao preferida):
     ALTER TABLE nodes RENAME COLUMN type TO origin;

     Nota: SQLite nao suporta RENAME COLUMN diretamente em versoes
     antigas. Alternativa:
     a. CREATE TABLE nodes_new (... origin TEXT NOT NULL DEFAULT 'file'...)
     b. INSERT INTO nodes_new SELECT id, ..., type AS origin, ... FROM nodes
     c. DROP TABLE nodes
     d. ALTER TABLE nodes_new RENAME TO nodes

     Ou, menos invasivo:

  2. Adicione alias na camada de logica:
     Em c:/Nexus-Memory/storage/logic.py, adicione:
     @property
     def origin(self):
         return self._data.get("type")

  3. Atualize todas as referencias em:
     - core/middleware.py (get_implementations, lazy_load)
     - storage/logic.py (GraphLogic)
     - services/janitor.py (generate_and_persist_community_summaries)
     - interface/mcp_server.py (respostas das tools)

  4. Adicione uma NOTA de depreciacao na documentacao: "type sera
     renomeado para origin na proxima major version"

9. SEM VERSIONAMENTO APPEND-ONLY
================================================================================

O que e:
  O sistema usa valid_from_commit / valid_to_commit para invalidar
  registros antigos (soft delete temporal), mas nao mantem versoes
  anteriores do conteudo. Quando um fato e atualizado, o registro
  antigo e marcado como invalido e um novo e criado — o historico
  existe, mas recuperar "como era antes" exige joins complexos.

Localizacao:
  - c:/Nexus-Memory/storage/semantic_logic.py:53-70 (invalidate + insert)
  - c:/Nexus-Memory/storage/logic.py: (valid_from/to nos calculos)
  - c:/Nexus-Memory/core/memory_extractor.py:165-168 (UPDATE bi-temporal)

Por que ocorre:
  O design usa bi-temporal puro (t_valid, t_invalid) que e correto
  para saber o que estava valido em determinada data. Porem, nao ha
  uma tabela de versoes que permita "diff" entre versoes ou rollback
  seletivo.

Impacto:
  - Impossivel ver "o que mudou" entre versoes de um fato
  - Rollback requer reinserir o statement antigo manualmente
  - Auditoria de mudancas depende de logs externos (commit_log)
  - Perda de contexto semantico sobre a evolucao do conhecimento

Como corrigir (passo a passo):

  1. Crie uma tabela de versionamento:
     CREATE TABLE node_versions (
         version_id   INTEGER PRIMARY KEY AUTOINCREMENT,
         node_id      INTEGER NOT NULL REFERENCES nodes(id),
         version_num  INTEGER NOT NULL,
         summary      TEXT,
         content      TEXT,
         created_at   TEXT NOT NULL DEFAULT (datetime('now')),
         commit_id    INTEGER REFERENCES commit_log(id),
         change_reason TEXT,  -- opcional: "update", "correction", "enrichment"
         UNIQUE(node_id, version_num)
     );

  2. No momento de atualizar um no (update_node), ao inves de
     sobrescrever summary/content, faca:
     a. Copie os valores atuais para node_versions
     b. Incremente version_num
     c. Atualize summary/content no node

  3. Adicione ferramenta concierge_get_node_history(node_id):
     Retorna todas as versoes do no ordenadas por version_num DESC

  4. Adicione ferramenta concierge_rollback_node(node_id, version_num):
     Reverte o no para uma versao anterior:
     a. Copia versao atual para node_versions
     b. Copia a versao desejada de volta para nodes
     c. Cria commit no commit_log documentando o rollback

14. JANITOR IDLE-LOCK BASEADO EM THREADING.EVENT()
================================================================================

O que e:
  O Idle-Lock do Janitor usa threading.Event() para detectar se
  mine() esta em andamento. Se a thread do mine travar, o Janitor
  espera 30s e depois pula o ciclo, mas se o Event nunca for
  liberado, o Janitor fica bloqueado indefinidamente.

Localizacao:
  c:/Nexus-Memory/services/janitor.py:141
    self._mine_active = threading.Event()

  c:/Nexus-Memory/services/janitor.py:179-196
    def _wait_for_idle(self):
        while self.is_system_active():
            if time.monotonic() - start > IDLE_LOCK_TIMEOUT:
                return False
            time.sleep(0.5)

Por que ocorre:
  O Event e confiavel para sinalizacao simples, mas se o mine()
  crashar apos chamar signal_mine_start() sem chamar signal_mine_end(),
  o Event fica setado permanentemente e o Janitor nunca executa
  manutencao.

Impacto:
  - Se mine() crashar: Janitor fica preso no Idle-Lock para sempre
  - Manutencao automatica para de funcionar ate restart do servico
  - Trajetorias stale nunca saem decaidas
  - Vetores orfaos nunca sao limpos

Como corrigir (passo a passo):

  1. Substitua o Event por uma abordagem com timeout absoluto:
     Em services/janitor.py, modifique:
     self._mine_active = threading.Event()
     self._mine_timestamp = 0.0  # timestamp da ultima sinalizacao

     def signal_mine_start(self):
         self._mine_active.set()
         self._mine_timestamp = time.monotonic()
         ...

     def is_system_active(self):
         if not self._mine_active.is_set():
             return False
         # Se passou mais de 5 minutos desde o start, considera orfao
         if time.monotonic() - self._mine_timestamp > 300:
             self._mine_active.clear()
             logger.warning("Idle-Lock: mine() orfao detectado (>5min) — liberando lock")
             return False
         return True

  2. Adicione um watchdog no background thread:
     A cada ciclo do Janitor, verifique se o Idle-Lock esta preso
     ha mais de 5 minutos. Se sim, libere automaticamente.

  3. Loggue sempre que o Idle-Lock for liberado por timeout,
     para monitoramento.

15. SEM VALIDACAO DE SCHEMA NAS TOOLS MCP
================================================================================

O que e:
  As tools MCP aceitam parametros que sao validados apenas no banco
  (CHECK constraints). Por exemplo, scope_type so sera validado quando
  a query SQL rodar, nao na chamada da tool.

Localizacao:
  - interface/mcp_server.py:379-394 (store_fact aceita qualquer string)
  - interface/mcp_server.py:404-421 (set_memory aceita qualquer scope_type)
  - storage/semantic_logic.py:38-39 (validacao ocorre aqui, tarde demais)

Por que ocorre:
  As tools MCP delegam toda a logica para a Fachada Central, que
  delega para o storage. A validacao so acontece na camada de storage,
  depois que a requisicao ja foi processada pelo MCP.

Impacto:
  - Erro so aparece no log, nao como resposta clara da tool
  - Usuario recebe erro generico em vez de dica de correcao
  - Custo de processamento desperdicado com requisicoes invalidas
  - Pior experiencia de uso

Como corrigir (passo a passo):

  1. Adicione validacao nas tools MCP antes de chamar a fachada:
     Em interface/mcp_server.py, em cada tool, adicione:
     VALID_SCOPE_TYPES = frozenset({"user", "session", "agent", "org"})

     def _handle_store_fact(self, scope_type, scope_id, fact_statement):
         if scope_type not in VALID_SCOPE_TYPES:
             return {
                 "success": False,
                 "error": f"scope_type invalido: '{scope_type}'. "
                          f"Aceitos: {sorted(VALID_SCOPE_TYPES)}"
             }
         if not scope_id or not scope_id.strip():
             return {"success": False, "error": "scope_id nao pode ser vazio"}
         if not fact_statement or not fact_statement.strip():
             return {"success": False, "error": "fact_statement nao pode ser vazio"}
         # ... chama a fachada

  2. Centralize as validacoes:
     Crie c:/Nexus-Memory/interface/validators.py com funcoes reutilizaveis:
     validate_scope_type(scope_type) -> Optional[str] (None ou msg de erro)
     validate_project_uuid(uuid) -> Optional[str]
     validate_node_type(node_type) -> Optional[str]

  3. Aplique validators em todas as tools MCP:
     - store_fact
     - set_memory
     - get_memory
     - register
     - search
     - commit

  4. Adicione testes unitarios para cada validator
